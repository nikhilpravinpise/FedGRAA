## Judgment-call table

| ID | Question | Choice | Rationale |
|---|---|---|---|
| JC-T7-1 | WeiDetect's `T` (top-T CDF selection count) — never given a formula or value; Algorithm 3 line 9 just says "select top T" | `T = round((1 - assumed_malicious_fraction) * M)`, with `assumed_malicious_fraction` a defense hyperparameter, default `0.3` | The paper supplies no rule at all. A defense cannot use the *true* attacker fraction (that would be oracle knowledge a real deployment doesn't have) — an *assumed* operating fraction is the realistic quantity, and `0.3` matches this project's own D5 field-standard attacker-fraction grid value, keeping the defense's assumption and the campaign's actual injection rate aligned at the grid's primary operating point |
| JC-T7-2 | WeiDetect's Weibull family — Eq. 11 gives a standard 2-parameter Weibull PDF; Algorithm 3 line 5 and the surrounding prose separately describe a 4-parameter *exponentiated* Weibull, with `T` reused as both the local variable and Algorithm 1's own communication-round count | 2-parameter Weibull (`scipy.stats.weibull_min.fit`, floc pinned to 0), per Eq. 11's explicit formula | Eq. 11 is the only place an actual PDF formula is written out; the "exponentiated Weibull" line names a different, more complex family with no formula given anywhere in the accessible text — implementing an unspecified 4-parameter family would be inventing math the paper never states, not reproducing it |
| JC-T7-3 | WeiDetect's `AD` (server-held auxiliary validation set, confidence > 0.9 predictions) | Built from this harness's existing pooled `ValidationSplit` (the same oracle pool `v1_projected`/FedGRAA-v1 already uses, never FedGRAA-v2's own privacy-compliant path) | WeiDetect's own design assumes server-side data access — that is a property of *this baseline method*, disclosed and reproduced as-is, not a deviation this reproduction introduces. It has no bearing on FedGRAA-v2's own mechanism, which stays privacy-compliant by construction regardless of what a T7 defense baseline requires to run at all (mirrors FedPGO's JC2 precedent of reusing the harness's existing oracle split for a baseline that structurally needs one) |
| JC-T7-4 | WeiDetect's `M` vs `N` (participating vs. total clients) | Full participation every round (`M = N`), matching every other trainer in this codebase | No trainer in this repository ever subsamples clients; the paper's own Table 1 setup (`N=20`) is silent on whether every round uses all 20, and full participation is this codebase's own universal convention (SCAFFOLD's JC-TC-5 makes the identical call for the identical reason) |
| JC-T7-5 | FLPoison/SoK's "attack strength" as a second harness knob — the phrase does not appear in the paper's own text; only attacker-fraction (`f/n`, swept 0.1-0.48) is a named, systematically-varied axis | The T7 harness (`scripts/run_v2_frontier_sweep.py`'s new tier) defines attacker-fraction as its primary swept knob (matching FLPoison's own ablation) and treats per-attack "strength" (label-flip fraction, pill perturbation scale) as an attack-specific parameter documented per attack, not as a second FLPoison-native axis | The master plan's own D4 already names attacker-fraction/attack-strength as "the two primary knobs" in general SoK/FLPoison-aligned terms; this JC entry corrects the specific claim that FLPoison's own paper text defines "attack strength" as one unified quantity — it does not, so this reproduction does not claim it does |
| JC-T7-6 | FLPoison's ACC/ASR metric definitions | Reused directly: `ACC` = fraction of correctly predicted test labels; `ASR` = fraction of *targeted, poisoned* test samples classified as the attacker's target — mapped in this codebase to rare-class recall (`ACC`-analogue, this project's metric of record) and a new `attack_success_rate` field | Both formulas are given verbatim in the paper (§6.1) and map cleanly onto this codebase's existing accuracy/rare-class-recall machinery |
| JC-T7-7 | Guo et al.'s camouflage scaling constants `C_up`/`C_down` (Algorithm 2) — no numeric value given anywhere in the accessible main text | `C_up = 1.05`, `C_down = 0.95`, `C_iter = 10` (max adjustment iterations), all disclosed constructor defaults | The paper defines the algorithm's *structure* precisely (alternating up/down scaling until similarity/distance targets are met) but the specific step size is absent from the extracted text (likely appendix-only); small, symmetric, disclosed defaults are the same category of judgment call FedPGO's JC5/JC6 already made for that paper's own untuned constants |
| JC-T7-8 | Guo et al.'s six named "dynamic search pattern" combinations (Table 2/Appendix C) | **Not implemented.** Only the core mechanism is reproduced: rule-1/rule-2 blueprint construction, greedy max-pill search (Step 2), and the camouflage adjustment (Algorithm 2) | The six-pattern combinatorics is a refinement on top of the base mechanism that the extraction could not confirm verbatim (partial surfacing only); implementing an unconfirmed table would be inventing detail the reproduction cannot verify against the source. Mirrors SpectralFed's own precedent (`fedgraa/baselines_t3_contrib.py`): the base mechanism is reproduced faithfully, the named refinement is explicitly out of scope, not silently approximated |
| JC-T7-9 | SecFedNIDS's hard-coded `contamination=0.4` (SOS outlier prior) and `>90`-of-100-clients consensus threshold — both specific to that script's own 100-client/up-to-40-malicious experimental configuration | Rescaled proportionally to this project's own client count `K`: `contamination = assumed_malicious_fraction` (`0.3`, same constant as JC-T7-1, kept consistent across both defense reproductions), consensus threshold `= round(0.9 * K)` | Neither constant is derived from a formula in the source — both are literal hard-codes tied to the reference script's specific setup. Rescaling proportionally (same fraction of the *actual* client count, not the original K=100) is the only defensible way to port a hard-coded constant to a different client-population size, and disclosing it here matches SecFedNIDS's own code-level (not paper-level) judgment calls named in the primary-source research pass |
| JC-T7-10 | SecFedNIDS's per-client importance statistic (`consolidate()`'s online path-integral `omega` accumulator) requires access to every local optimizer step's gradient and parameter delta — this codebase's existing fused XLA client-training step (`_fused_client_step`) is a compiled `tf.function` that does not expose per-step state back to Python | New instrumented fused step, `_fused_importance_step` (`fedgraa/model.py`), that accumulates `omega[n] += max(-grad[n] * (p_after[n] - p_before[n]), 0)` into a passed-in `tf.Variable` list at every local step, mirroring `_fused_scaffold_step`'s own pattern of adding one instrumentation/correction concern to the shared fused-step family | The alternative — reverting to an uninstrumented, non-fused per-step Python loop just for SecFedNIDS — would silently change this baseline's own runtime characteristics relative to every other trainer in the codebase; adding one more fused-step variant keeps the instrumentation faithful to the source *and* consistent with every other baseline's performance profile |
| JC-T7-11 | SecFedNIDS's `iid()` client-partitioning function (actually non-IID by construction, a naming mismatch in the source itself, per the primary-source research) | **Not ported.** This project's own `partition_non_iid` is used for every T7 cell, exactly as it is for every other arm | SecFedNIDS's detection *algorithm* (importance accumulation, top-K consensus filter, SOS clustering) is the thing being reproduced, not its data-partitioning scheme — every T3/T5/TC baseline in this codebase already runs on this project's own partitioner rather than each paper's own, and T7 follows the same established convention |
| JC-T7-12 | SecFedNIDS's data-level detection path (`main_poisoned_data_det.py`'s neuron-path-IoU sample filter, a secondary mechanism gated behind the model-level filter) | **Not implemented.** Only the model-level poisoned-client detection (`defence_our`) is reproduced | The master plan's D2 names SecFedNIDS as a *client-level* defense baseline (parallel to WeiDetect and AdaAggRL); the data-level, per-sample filter is a distinct secondary mechanism in the reference repo that the master plan never scoped in, and implementing it would silently expand D2's own decision rather than execute it |
| JC-T7-13 | D1c (the mechanism-specific rare-class-signature attack) needs a precise mapping from FedGRAA-v2's own up-weighting signal onto a concrete, exploitable quantity | **Read `dL'/dw_k = <grad_P, P_k>` directly off `fedgraa/aggregation.py::_grad_wrt_weights`** (FedGRAA-v2's *actual*, exact weight-update gradient) rather than the literature review's own informal "orthogonal-component norm" language. The attack constructs `P_fake = P_global - eta_fake * grad_P` (a literal step in the negative composite-gradient direction) — by construction `<grad_P, P_fake> = <grad_P, P_global> - eta_fake*\|\|grad_P\|\|^2`, strongly negative, which Adam's descent on `w` turns directly into a large weight increase, exactly the "gets up-weighted by construction" claim `STAGE_C_LITERATURE_MASTER.md` line 398 makes | This is genuine new design work, not a reproduction — the master plan's §2.4 item 1 already flags this explicitly. Deriving the attack from the mechanism's own printed formula (rather than the lit review's own paraphrase of it) is strictly more faithful: it is testable in closed form (§2.7 item 4's regression test: the attacker's weight *provably* increases vs. an honest delta of the same underlying gradient) rather than only approximately true of an informally-described "orthogonality" proxy |
| JC-T7-15 | D1c needs `grad_P` to construct its poisoned contribution, but the real `grad_P` for the *current* round is only known after `FedGRAAv2.update()` has already consumed `client_params` (circular: the attack would need the round's own output as its input) | The attacker uses `trainer._last_grad_P`, the most recently *measured* composite gradient from the previous grad-refresh epoch — the same quantity FedGRAA-v2's own two-phase protocol already broadcasts to every client as `theta'_g` traffic (billed in `bytes_sent`, `fedgraa/trainer.py`'s `grad_provider`). Round-1 (no prior `grad_P` yet) falls back to an honest, unmodified contribution | A real attacker cannot see the future; using the last *actually broadcast* quantity is the realistic "informed insider" threat model, not an oracle one, and mirrors FedPGO's own JC4 precedent for round-1 degeneracy (fall back to the degenerate-but-defined case rather than special-casing it away) |
| JC-T7-14 | D1d (AutoAdapt-style adaptive attacker) — Krauß et al., NDSS 2024, not read this pass (master plan's own priority ordering: lowest of the four attacks, checked only once D1a-c are green) | Implemented as a generic wrapper (`adaptive_attack(defense_fn, ...)`) that optimizes a base attack's parameters against a *mocked* defense score function via random-restart local search, not against AutoAdapt's own specific optimizer, pending that paper's own read | Disclosed placeholder-with-real-mechanics, not a stub: the wrapper genuinely adapts against whatever defense score function it's given (pinned by the master plan's own test spec item 8), it simply doesn't yet claim fidelity to AutoAdapt's own specific optimization procedure — that fidelity gap is named here rather than silently assumed away |

| JC-T7-16 | D1b/c/d (model-poison, mechanism-specific, adaptive attacks) are parameter-space attacks -- they poison a client's *trained update*, not its input data -- but AdaAggRL (D2's reused-not-reimplemented defense) has its own existing, deliberately-unmodified T5 implementation (`fedgraa/baselines_t5_adaptive.py`) whose internal per-round client-training call is not exposed as a hookable seam without editing that class, which the master plan's own §2.7 test item 7 says must not happen | **AdaAggRL is evaluated under D1a (label-flipping) only.** D1a poisons `ClientShard.y_train` *before* any trainer runs, so it applies to AdaAggRLTrainer with zero modification -- exactly what test item 7 asks for ("receives attacker-fraction metadata without requiring changes"). D1b/c/d run against the two new defense reproductions (SecFedNIDS, WeiDetect, built with attack-injection hooks from the start) and, for D1c specifically, against FedGRAA-v2 itself (the master plan's own trend-line addendum, §2.5) | This narrows the literal 4-attacks x 3-defenses full cross-product for one cell of the grid (AdaAggRL x {D1b,D1c,D1d}) rather than silently building a bespoke, never-independently-tested hook into code the plan explicitly says must stay unmodified. Named here rather than left as an unstated gap in the campaign's actual cell count (§2.5's 120+20=140 total is reduced by AdaAggRL's 3 excluded attack types x 2 datasets x 5 seeds = 30 cells it would otherwise have contributed, i.e. **110 cells**, not 140 -- corrected here rather than silently run smaller than documented) |

| JC-T7-17 | Which clients are attackers -- resampled every round, or fixed for the whole run? | **Fixed for the whole run**, deterministic given `cfg.seed` (`rng.choice` over client indices at construction time) | Matches the field-standard poisoning-attack threat model (a persistent, not intermittent, adversary controlling the same `attacker_fraction` of clients throughout) and every attack/defense reproduction's own implicit assumption (SecFedNIDS's reference script injects poisoning "in the final round" for up to a fixed `num_poison_client`, not a resampled set) |

| JC-T7-18 | Should D1c (`rare_class_signature_attack`) also run against the SecFedNIDS/WeiDetect defense cross-product, as a literal reading of §2.5's "4 attacks x 3 defenses" would imply, in addition to the undefended-FedGRAA-v2 trend addendum? | **No.** D1c is evaluated *only* via the trend addendum, against undefended FedGRAA-v2 -- never against SecFedNIDS/WeiDetect | D1c is calibrated specifically to FedGRAA-v2's own printed weight-update formula (JC-T7-13); against a defense that doesn't use that formula at all, its fabricated `P_global - eta*grad_P` update would exercise nothing method-specific -- it would just look like a generic small perturbation, redundant with D1b's own coverage of that defense. Testing it there would burn compute without adding a distinct signal. **Final T7 grid, corrected from §2.5's 140/110 estimates:** defense cross-product = 2 datasets x {D1a,D1b,D1d} x {SecFedNIDS,WeiDetect} x 5 seeds (60) + 2 datasets x D1a x AdaAggRL x 5 seeds (10) = **70 cells**; D1c trend addendum = 2 datasets x 2 attacker-fractions x 5 seeds, undefended FedGRAA-v2 only = **20 cells**. **Total: 90 cells**, documented once here rather than left inconsistent across this table's own running arithmetic |
